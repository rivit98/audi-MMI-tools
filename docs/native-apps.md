# Native apps for the MMI 3G+: developer guide

How to write, build, run and debug your own C and C++ programs on the Audi
MMI 3G+ head unit: screen, GPU, sound, hardware video, input and USB. It
collects what was confirmed on the car. The
deep dives are linked from each section.

**Scope.** Everything was measured on one unit: MMI 3G+ 9411, train
HN+R_EU_AU_P1001, MU 1072, board E1 (firmware tree `51`). The platform
facts (CPU, QNX, protocols) apply to the whole 3G+ family. Anything tied to
a binary (stub libraries, RE addresses) is for P1001 rev 51 and has to be
checked again on other trains.

**Labels.** *confirmed* = measured on the car or read from the unit's
binaries. *inferred* = follows from confirmed facts but hasn't been
exercised. *unverified* = an assumption.

---

## 1. Quick start

```sh
make sdk                          # once: mmi-sdk Docker image (cross-GCC + QNX sysroot)
make sd SD_APPS="hello7"          # build + lay out an SD card in build/sd/
# copy the CONTENTS of build/sd/ to the root of a FAT32 card,
# boot the MMI fully, insert into SD slot 1
```

The card shows a start screen, then runs the apps one after another, each
followed by its result screen. Logs come back in `var/` on the card. If the screen
freezes, reboot the MMI: hold **MENU + rotary knob + top-right soft key**.

## 2. The platform

| | |
|---|---|
| CPU | Renesas SH7785 (SH-4A), 792 MHz, **one core**, little endian, FPU |
| OS | QNX Neutrino 6.3.2 (build 3262), `libc.so.2` (Dinkumware), loader `/usr/lib/ldqnx.so.2` |
| Display | 800×480 `BGRA8888`, 60 Hz, 8 hardware layers (apps get layer 7, the top one) |
| Compositor | `layermanagerV2` at `/dev/layermanager` (devctl protocol, §8) |
| GPU | NVIDIA NV18 (GeForce4 MX class), **OpenGL ES-CM 1.0** fixed function, EGL 1.3 |
| Video | TI DM642 DSP behind `io-media-nvidia`: H.264 BP, MPEG-2, MPEG-4 (§10) |
| Audio | io-media mixer on the DSP → TDM → MOST amplifier (§11) |
| Input | `/dev/ipc/ch8`: knob and button state messages (§12) |
| USB | `io-usb` (EHCI + OHCI), client library `libusbdi.so.2` (§13) |
| Clock | starts at 1970 on every cold boot |

## 3. How the toolchain works

There is no QNX SDK. Only GCC's code generator is used, and every
OS-specific input is replaced:

| Layer | Linux SH4 GCC default | Replaced by |
|---|---|---|
| Instructions, calling convention, FPU ABI | Renesas SH ELF ABI | kept: the same on QNX |
| Headers | glibc | openqnx (QNX 6.4.1 source) public headers, `-nostdinc`, 64-bit alignment patched back to 6.3.2 |
| Startup | glibc crt | openqnx `crt1.S`/`crti`/`crtn`/`crtbegin`/`crtend`, plus `sdk/crtarray.c` (the init/fini array runners lived in QNX's closed static libc) |
| Libraries | glibc `.so` | **stubs** of the unit's own `.so` files, generated by `sdk/mkstubs.py` |
| Loader, ELF | PIE, GNU hash | ET_EXEC at `0x08040000`, SysV hash, `-z now`, 4 KB pages, interpreter `/usr/lib/ldqnx.so.2` |

The firmware's libraries can't be linked against directly: mkifs stripped
their section headers. Their dynamic segment is intact (the QNX loader needs
it), so `mkstubs.py` walks `PT_DYNAMIC` → `DT_HASH`/`DT_SYMTAB`/`DT_STRTAB`
and writes a stub with the same SONAME, symbols and data-object sizes (for
`R_SH_COPY`, e.g. `errno`). The app links against the stub. On the car the
real library loads.

Stubbed today: `libc.so.2`, `libm.so.2`, `libgf.so.1`, `libEGL.so.6`,
`libGLES_CM.so.6`, `libasound.so.2`, `libusbdi.so.2`. To add one, append it
to `FWLIBS` in the Makefile and run `make sdk`. Two quirks: the device's
`libc.so.2` exports GCC's SH helpers itself (`__set_fpscr`,
`__fpscr_values`, `__sdivsi3_i4`), and it exports the linker-reserved
`_DYNAMIC` and `_GLOBAL_OFFSET_TABLE_`, which `mkstubs.py` leaves out.

The result matches the stock binaries:

| | stock `/bin/cat` | qnx-audi (`qcc`) | ours |
|---|---|---|---|
| Type / base | `EXEC` @ `0x08040000` | `EXEC` | `EXEC` @ `0x08040000` |
| Interpreter | `/usr/lib/ldqnx.so.2` | same | same |
| Symbol hash | SysV | SysV | SysV |
| Bind | — | `FLAGS_1 NOW` | `FLAGS_1 NOW` |
| Data imports | — | `R_SH_COPY` (`errno`, …) | `R_SH_COPY` (`errno`, `_Stdout`, …) |
| e_flags | `0x8` (sh3e) | — | `sh4a` (the loader only checks `e_machine`) |
| `PT_GNU_STACK` | no | — | yes (GNU ld always emits it; the loader ignores it) |

Headers with no public source were reconstructed and are locked by
`_Static_assert`s: `sdk/include/gf/` (QNX GF: signatures from the 6.4.1
docs, layouts from the STABS in qnx-audi's 6.3.2-built `dbg-shle.elf`,
`GF_ERR_*` and flag values from its disassembly; the 6.4 docs are wrong
for 6.3.2: `gf_dev_info_t` has `reserved[6]` instead of vendor/device ids,
and `vaddr` comes before `paddr`),
`sdk/include/sys/asoundlib.h` (QSA, from the unit's `libasound`), and
`sdk/include/sys/usbdi.h` (from the QNX 6.5 header, checked against the
unit's `libusbdi`).

**The compiler wrapper** `sdk/shle-nto-gcc` (and `shle-nto-g++`, a link to
it) behaves like gcc. What it adds, and why:

| Flag / step | Why |
|---|---|
| Debian sid `gcc-16-sh4-linux-gnu` | GCC 12.2 drops the second test of `a == 0 && b == 0` at `-O1`+ ([gcc-sh4-treg-bug.md](gcc-sh4-treg-bug.md)). `build/.canary` fails the build if a later GCC 16.x brings it back. |
| `-m4a -matomic-model=hard-llcs -Wa,--isa=sh4a` | SH-4A LL/SC atomics. GCC's sh4 default (gUSA) **loses updates** on QNX, whose kernel doesn't restart gUSA sequences: 9–64 % lost on the car, LL/SC 0 %. The loader accepts the `sh4a` ELF flag. |
| `-U_FILE_OFFSET_BITS -U_TIME_BITS` | GCC 14+ on Debian predefines 64-bit `off_t`/`time_t`, which turns `open()` into the missing `open64()`. |
| `-fno-builtin-sin*/cos*` | GCC fuses `sinf`+`cosf` into `sincosf`, which QNX's libm lacks. |
| `-D__QNX__ -D__QNXNTO__ -D__SH__ -D__LITTLEENDIAN__`, Linux macros undefined | What the QNX headers key on. |
| `-DEGL_NO_PLATFORM_SPECIFIC_TYPES` | EGL native types become `void*` (on QNX GF they are `gf_dev_t`/`gf_3d_target_t`). |
| `-fno-pie -fno-stack-protector` | QNX 6.3 loader expects ET_EXEC; no SSP runtime. |
| `sdk/qnx-elf-fix.py` after every link | Rewrites `STB_GNU_UNIQUE` → `GLOBAL` (ldqnx: "unknown symbol") and OSABI. **Fails and deletes the binary** on TLS or IFUNC, so a binary the loader would reject never reaches the card. |

## 4. Build system

Everything runs in Docker. No host toolchain is used.

| Image | Built from | Used for |
|---|---|---|
| `mmi-sdk` | `Dockerfile` | cross-compiler, sysroot, host `gcc` for unit tests, `sh4-linux-gnu-objdump`/`addr2line` |
| `mmi-media` | `media/Dockerfile` | ffmpeg: test clips (`media/mkclips.sh`, `media/csmp4.py`) |
| `mmi-android` | `android/docker/Dockerfile` | Kotlin/Gradle phone app, `adb` (own `android/Makefile`) |
| `mmi-aoa-host` | `tools/Dockerfile.aoa-host` | desk stand-in for the MMI's USB side (`tools/aoa_host.py`) |

`make sdk` needs two inputs from the toolkit checkout, passed as narrow
build contexts so the firmware tree is never sent to Docker:

- `third_party/openqnx/trunk`: the openqnx source (headers + SH startup code).
- `third_party/HN+R_EU_AU_P1001/extracted/MU9411/{ifs-root,efs-system}/51/`: the
  extracted firmware, the source of the stubbed `.so` files and of the
  unit's own tools (`efs-system` binaries inflated with
  `tools/qnx_inflator.c`; `tools/f3swalk.py` extracts whole efs images).

The Makefile expects to sit two levels below the toolkit root (`REPO :=
../..`), because `make sd` uses the toolkit's `builder/encoder.py` and
`core/` (autorun launcher, `showScreen`).

| Target | Does |
|---|---|
| `make sdk` | build `mmi-sdk` (again after changing `sdk/` or `FWLIBS`) |
| `make` | all apps into `build/` (unstripped, `-O2 -g`) |
| `make sd [SD_APPS="a b"]` | card layout in `build/sd/`: only those apps plus their clips, unit tools and files |
| `make test` | host unit tests (`tests/*.c`, `*.cpp`) with ASan/UBSan |
| `make check APP=x` | ELF header, interpreter, NEEDED, flags of `build/x` |
| `make addr APP=x ADDR="0x08043270 …"` | crash address → function, file:line |
| `make gusa-scan` | gUSA atomic sequences left in each binary |
| `make clips` | test videos into `build/clips/` |
| `make apk` / `apk-test` / `apk-install` | Android app (`android/out/audi_streaming.apk`), its tests, `adb install` from the container |
| `make aoa-host` | desk test of the phone app over the PC's USB (stop host `adb` first) |
| `make shell` | shell in the SDK container |

Outside the Makefile, the wrapper works like gcc:

```sh
docker run --rm -u $(id -u):$(id -g) -v $PWD:/src mmi-sdk \
    shle-nto-gcc -O2 -g -Wall -o app app.c -lgf
```

```

                        reconstructed headers (include/), C++ overlay + shim,

media/                  test clip generators
```

### Adding an app

1. Put the code in `src/myapp/` (plus a short `README.md`).
2. In the Makefile, add it to `APPS` and give it a rule naming the
   `src/common` groups it uses and the device libraries:

   ```make
   APPS := ... myapp
   build/myapp: $(wildcard src/myapp/*.c src/myapp/*.h) $(BASE) $(SCREEN)
   LIBS_myapp := -lgf
   ```

   For C++, also add it to `CXX_APPS` (the rule compiles the `src/common`
   files as C and yours as C++ in one command).
3. Add a line to `sd/apps.conf`:
   `name|timeout s|arguments after <sd>|title|what you see / do`.
4. `make test` for the host-testable parts, then `make sd SD_APPS=myapp`.

| Group | Files | Gives you |
|---|---|---|
| `BASE` | `log`, `quit`, `lmgr` | SD log, clean-stop sources, layer manager client |
| `TEXT` | `text` + generated fonts | UTF-8, word wrap, Terminus 8×16 / 16×32 glyphs |
| `SCREEN` | `screen`, `vfbcopy` + `TEXT` | a CPU-drawn full-screen displayable |
| `GL` | `gfx`, `hud`, `img` | gf + EGL bring-up, FPS counter, BMP/PNG writer |
| `IMG` | `img` | PNG/BMP writer (stb_image_write) |
| `IMGDEC` | `imgdec` | JPEG + PNG decoder (stb_image) |
| `PROC` | `proc` | start the unit's own tools from a threaded app |
| `IOM` | `iom` | own io-media client: sound, video playback |
| `CPUMON` | `cpumon`, `cpustat` | own + whole-unit CPU load lines |

Keep logic that doesn't touch the car's APIs in pure files and test it on
the host (`tests/test_*.c`): protocol parsing, decoding, layout, stream
planning. A FAIL on the car is then the car, not the code.

## 5. Running on the car

**Autorun chain** (from the toolkit): `proc_scriptlauncher` finds
`copie_scr.sh` on the card (XOR-encoded by `builder/encoder.py`) → it runs
`core/copie_scr_plain.sh` → `cd $SDPATH; exec ksh ./run.sh $SDPATH`.

**`sd/run.sh`** (ksh; no native runner needed):

- copies `bin/*` to `/tmp/mmi_apps/` and runs from there (FAT32 has no
  exec bit, and the card can be pulled mid-run);
- a start screen, then per app: the app with stdout/stderr in
  `var/<app>_out.log` → its result screen. Screens are drawn on the car: `screens.sh` prints a
  layout, `bin/pngondemand` renders a PNG, `showScreen -t` shows it;
- enforces the `apps.conf` timeout (TERM, KILL 15 s later);
- saves `sloginfo` to `var/<app>_slog.txt` and moves core files to `var/`;
- writes verdicts to `var/summary.txt`: `OK` (exit 0, no `FAIL` line),
  `WARN` (exit 0 with `FAIL` lines), `FAIL`, `CRASH` (signal = exit −
  128), `TIMEOUT`, `MISSING`.

Apps get the card path as `argv[1]` and write their own logs there.
`sd/apps.conf` holds each app's timeout, arguments and title; the start
and result screens last `PRE_S`/`POST_S` (Makefile). Screen rendering time
counts towards them, and if pngondemand or showScreen fails, `run.sh`
sleeps the rest, so timing never changes (errors in `var/run.log` and
`var/showscreen.log`). When `showScreen -t` ends the HMI comes back, and the
next app can take the screen at once (confirmed). If neither
the apps' output nor `var/run.log` appears, `copie_scr.sh` didn't run.

**Crashes.** The unit runs the "Audi 3G+ dumper"
(`dumper -m -w -z 1 -c -d /HBpersistence/core -d /mnt/persistence -f …`).
It writes `<name>.core*` (gzip, reduced dump for our apps) to
`/HBpersistence/core` (on flash; falls back to `/mnt/persistence`, then
`/tmp`) and a `run fault pid … ip 0x…` line plus a backtrace to slog;
`run.sh` moves our cores to `var/` so they don't fill the flash. Apps are
ET_EXEC and unstripped, so
`make addr APP=x ADDR=0x…` resolves an address inside the app directly. An
address outside `0x0804xxxx` is in a shared library: take `mapaddr` from the
slog line and disassemble that window of the firmware `.so` as raw binary
(the `.so` files have no section headers):

```sh
dd if=libGLES_CM.so.6 of=w.bin bs=1 skip=$((0x32600)) count=256
sh4-linux-gnu-objdump -D -b binary -m sh4 -EL --adjust-vma=0x32600 w.bin
```

Modern GDB has no QNX/SH support. Read cores with `readelf -n`/`-l`.

## 6. App skeleton and process rules

```c
#include <stdio.h>
#include <unistd.h>
#include "log.h"
#include "quit.h"
#include "screen.h"
#include "font_big.h"

int main(int argc, char *argv[])
{
	char path[256];
	snprintf(path, sizeof path, "%s/myapp.log", argv[1]);
	log_open(path);                        /* fsync per line */
	quit_init_ex(argv[1], 60 + 20, NULL, NULL);  /* before any other thread */
	if (screen_open() != 0) {
		log_msg("FAIL screen_open");
		quit_request(QUIT_TIMER);
	}
	unsigned end = log_ms() + 60000;
	while (log_ms() < end && quit_poll() == QUIT_NONE) {
		struct canvas *c = screen_canvas();
		canvas_fill(c, 0, 0, c->w, c->h, 0xff101820u);
		text_draw(c, &font_big, 20, 20, "hello", -1, 0xffffd040u);
		screen_present();
		usleep(100 * 1000);
	}
	screen_close();                        /* gives the screen back to the HMI */
	log_close();
	return 0;
}
```

`src/hello7/main.c` is a complete, small example (screen + knob callback).

`quit.c` stops an app on its timer, SIGTERM/INT/HUP (via a `sigwait()`
thread), SD removal (checked once a second) or a watchdog (`alarm()`).
After a stop request the app has 10 s, then `_exit()`. No key stops an app.

Rules the platform forces:

- **Divide by zero is a fatal `SIGFPE`**, float and integer alike. QNX
  enables the FPU's divide trap (`crt1.S` sets FPSCR `0xc0400`, and the
  kernel too) because SH integer division runs on the FPU. `x/0.0f` is not
  `inf`. Guard every denominator. The GL driver has unguarded divides too
  (linear fog: use `gfx_fog_linear()`). [qnx-sh-fpu-div0.md](qnx-sh-fpu-div0.md)
- **No `fork()` in a threaded process** (QNX 6.3 refuses it). Start
  children with `spawnvp(P_NOWAIT)`: `proc_start()`/`proc_shell()`.
- **No signal handlers.** Block signals and `sigwait()` in a thread, so GL
  and gf calls never see `EINTR` (and C++'s precompiled gUSA code can't be
  hit, §7).
- **No TLS** (`thread_local`, `__thread`): the build stops on it.
- **No `math.h`** in the sysroot: declare what you need or use
  `src/common/qnx/math.h`, and link `-lm` (the unit's C99 `libm.so.2`).
- **64-bit types are 4-byte aligned** (QNX 6.3.2 ABI). Structs shared with
  device libraries depend on it.
- **SD writes are slow:** ~12 ms per fsync'ed line, ~140 KB/s. Keep
  `log_msg` out of per-frame paths. Put records in a RAM ring and let a
  low-priority thread write them (`src/audi_stream_receiver/perf.c`).
- `/tmp` takes files (binaries, WAVs that io-media plays), but `mkdir
  /tmp` and `rm -rf /tmp/…` report errors. The shell has no `sync` or
  `touch` (`: > file`).
- `system_clock` is 1970 after a cold boot. Use `CLOCK_MONOTONIC`
  (`log_ms()`, `log_us()`). The tick is often 1 ms.
- CPU load: `cpumon.c` reads `DCMD_PROC_INFO`/`DCMD_PROC_TIDSTATUS` on
  `/proc/<pid>/as`; idle comes from procnto (pid 1). Measured: the unit is
  ~25 % busy with the HMI alone, 50–65 % while streaming pictures.

## 7. C++

C++20 with GCC 16's libstdc++ works: all 18 checks of `hello8` passed on
the car (static init, exceptions, RTTI, containers, algorithms, strings,
`<chrono>`, `<random>`, threads, mutexes, condition variables, atomics).
`shle-nto-g++` links `libstdc++.a` statically (~180 KB for an empty
`main`). The car's own `libstdc++.so.5` (GCC 3.3) and Dinkumware
`libcpp.so.4` don't match modern headers. Don't link them. A header overlay
(`sdk/include-c++/`) and a runtime shim (`sdk/cxxrt*.c*`: TLS-free
exception globals, `_dl_find_object`, QNX-layout `condition_variable`)
bridge the glibc-built library to QNX's libc.

| Not available | Use instead |
|---|---|
| iostreams, `<sstream>`, `<format>`, `std::locale`, `<filesystem>` (glibc locale code) | `snprintf`, stdio, POSIX `stat`/`opendir`, `log.h` |
| `std::async`, futures, `latch`/`barrier`/semaphores, `atomic::wait` (Linux futex) | `thread` + `mutex` + `condition_variable` |
| 64-bit `std::atomic` (needs libatomic) | 32-bit atomics or a mutex |
| `thread_local` | pass state explicitly |
| default `std::random_device` | `std::random_device("/dev/urandom")` |

Run-time rules:

- `std::atomic` and `shared_ptr` in your code are LL/SC and safe.
- The precompiled parts of `libstdc++.a` still use gUSA. So: don't share
  copies of a `std::runtime_error`/`exception_ptr` between threads (pass
  `what()` as a string), start threads from one thread, and install no
  signal handlers.
- An exception thrown through a C callback (`qsort`, `pthread_once`, a
  `call_once` body) calls `std::terminate`: QNX's libc has no unwind tables.
- `src/common` headers have no `extern "C"`: wrap the includes.
- Costs on the car: throw+catch through 11 frames 70 µs, 10k `std::map`
  inserts 29 ms, mutex lock+unlock ~0.2 µs.

Details: [cpp-apps.md](cpp-apps.md), [`sdk/include-c++/README.md`](../sdk/include-c++/README.md).

## 8. Screen: the layer manager (CPU drawing)

Every app that shows something registers a **displayable** with
`layermanagerV2` and draws into its virtual frame buffer (VFB), a gf
surface. `src/common/lmgr.c` is the client, `screen.c` the full-screen
CPU canvas on top of it. Protocol (from qnx-audi, unchanged in P1001):

| devctl | Meaning |
|---|---|
| `0xC0140500` | `REGISTER_DISPLAYABLE {cid, w, h, flags}`; success = rc 0 **and** `data[4] == 1` |
| `0x80040501` | `UNREGISTER_DISPLAYABLE {cid}` |
| `0xC0100503` | `GET_VFB {cid}` → `{sid, uid, alpha_sid}` |
| `0x80040504` | `UPDATE_VFB {cid}`: present |
| `0x800C0505` | `SHOW_DISPLAYABLES {display, n, cids…}` (a setter: an empty list blanks the screen) |
| `0xC00C0506` | `CHECK_VERSION` → 1.1 |

Sequence (DrGER's `showScreen`, confirmed): unregister 40 → register cid
40, 800×480, flags 2 → `GET_VFB` → attach the surface with gf, draw →
`UPDATE_VFB` → show `{40}`. On exit: unregister 40, show `{40, 16, 19}`
(the HMI's list, copied from showScreen).

- **The VFB is double-buffered.** `GET_VFB` returns the back surface and
  `UPDATE_VFB` flips. Call `GET_VFB` again after **every** update and draw
  into the new sid. Otherwise every other frame shows a never-written
  surface (pink/beige band noise).
- **Displayables outlive their client.** Closing the fd or crashing doesn't
  unregister. Always unregister your cid before registering it.
- Rejections come back as `EINVAL` plus `<ERR>` lines in slog.
- Don't hardcode `alpha_sid`: it changes every run.
- **The HMI can take the screen back.** MENU, BACK and MEDIA make it show
  its own screens over yours, and nothing tells you. An app that must stay
  up re-shows itself on a timer: `screen_set_reshow(ms)` (built, not yet
  confirmed on the car).
- **CPU writes into the VFB are slow:** ~9 MB/s, so a full 800×480×4 copy
  takes ~160 ms (main RAM: memcpy 107 MB/s). Draw into a RAM canvas and
  copy only what changed: `screen_set_partial(1)` keeps a shadow of each
  VFB surface and writes the changed span of each row. That took the
  stream receiver's copy from ~160 ms to ~18 ms.
- **Text commands** (`write()` to `/dev/layermanager`):
  `s-shot <display> <file>`, `d-shot <cid> <file>`, `da-shot <cid> <file>`
  (type by extension: png/bmp/jpg/gif). These capture the HMI and CPU-drawn
  VFBs, **never GL output**. `v-level` / `s-level` also exist; meaning
  unknown.
- Pictures: `imgdec.c` (stb_image) decodes JPEG/PNG to ARGB, `img.c`
  (stb_image_write) writes PNG/BMP. The SDK has no zlib or libpng.
  `pngondemand` renders a small text-layout language to PNG
  ([src/pngondemand/README.md](../src/pngondemand/README.md)).

## 9. GPU: 2D and 3D with OpenGL ES 1.0

`gfx_init()` (a port of qnx-audi's bring-up) registers cid 40, gets the VFB,
attaches gf device/display/layer 7, creates a `gf_3d_target` on the VFB
surface, then EGL (`EGLNativeDisplayType` = `gf_dev_t`, window =
`gf_3d_target_t`). `gfx_swap()` = `glFinish` + `eglWaitGL` +
`eglSwapBuffers`. `gfx_shutdown()` hands the screen back. Link
`-lGLES_CM -lgf` (P1001 ships NVIDIA's `libGLES_CM.so.6`, not the `.so.1`
older qnx-audi builds wanted).

| | |
|---|---|
| API | ES-CM 1.0 (float + fixed), **no shaders** |
| Texture | max 2048, **2 units**, power-of-two, S3TC/DXT1, `GL_OES_draw_texture` |
| Lights / clip planes | 8 / **0** |
| Depth / stencil | 24 / 8, but **ask for stencil explicitly** (`EGL_STENCIL_SIZE 8`), or `eglChooseConfig` picks a config without it |
| Offscreen | **no FBO**; pbuffers exist (all 8888 configs: window, pixmap, pbuffer) |
| Buffer objects | VBO extension advertised, but `glBindBuffer` not exported: use client arrays |
| Useful extensions | `GL_EXT_timer_query` (true GPU time), `GL_NV_fence`, `GL_EXT_bgra` |

Performance and safety (confirmed):

- **Everything is vsync-locked.** Frame times are multiples of 16.7 ms,
  so fps numbers measure quantisation. Use `GL_EXT_timer_query` for real
  costs.
- **Fill:** about 2 full-screen blended textured layers per 60 Hz frame.
- **Geometry is the weak point:** under 0.2 M lit triangles/s (the
  transform or vertex copy seems to run on the SH4). Budget: **under ~1000
  lit triangles per frame** for 60 fps.
- **The GPU can freeze the whole unit** (picture, knobs, volume; only the
  reboot combo helps). Seen with 16 lit tori (~314 KB of client arrays per
  frame) and with several big texture uploads queued between `glFinish`
  calls. Safe: 12 tori (~150 KB/frame), and **one upload in flight,
  `glFinish` after each**.
- **Uploads:** 800×480 RGBA `glTexSubImage2D` + `glFinish` in 31 ms
  (~50 MB/s, 5× faster than CPU writes into the VFB).
- **Capture GL output with `glReadPixels` only.** Layer-manager shots
  never contain it.
- The whole fixed-function pipeline (depth, culling, perspective,
  lighting, textures, mipmaps, fog, blend, stencil) passes pixel-readback
  probes (`src/hello4/probe.c`).

Details: [gpu-results.md](gpu-results.md), [platform-notes.md](platform-notes.md) §4–7, §10.

## 10. Video: the DM642 hardware decoder

`io-media-nvidia` drives a TI DM642 DSP (codecs loaded at boot from
`/etc/NvDspCodecs.elf`). An app plays a file through io-media and shows the
decoded picture on a **video displayable**.

**What plays (confirmed on the car):** MPEG-2 720×576 (`.mpg`), MPEG-4
Part 2 640×480 (`.avi`), H.264 Baseline 720×480 and 720×336 in plain MP4,
with or without audio.

**What doesn't:** wider than 720 or taller than 576 (io-media refuses it
before the DSP: `FUN_080d1760`), more than 25 fps above 480 lines,
H.264 above Baseline Level 3, fragmented MP4, H.264 in MPEG-PS, and growing
files. They fail at start with `iom_errno 0x80002` ("no metadata": the
track never opened). io-media's own MP4 demuxer (`CDemuxMp4`) reads
**32-bit box sizes only**, wants `moov` before `mdat`, loads every box but
`mdat` at open, and has a 10 MB header budget.

**Showing it** (`src/common/vout.cpp`):

```
lm: unregister 41; register {41, 800, 480, flags 0x101}; show {41}; wait 500 ms
open("/dev/videoctrl"):
  devctl 0x80080501 SET_SOURCE {vp 1, source 1}   VCAP 0 → input 1 = the DSP's video port
  devctl 0x8008050b ENABLE     {vp 1, 1}
  devctl 0x80040507 UPDATE     {0}
teardown: source 0, enable 0, update; unregister 41
```

- Register flags: bit 0 = video displayable, bit 8 = VCAP 0, bit 9 =
  VCAP 1. VCAP 1 ("Partial Decode") stayed black for every codec.
- The videoctrl payload must be exactly 8 bytes. A wrong one returns `EOK`
  and does nothing.
- VCAP scales the decoded picture to the displayable's size.
- Video is one global resource in io-media: your playback and the HMI's
  exclude each other. VCAP 0 input 0 is the rear-camera input (ADV7180):
  reversing showed the camera picture during a test.
- CPU stays 48–61 % idle during decode.

**Playing** goes through the same io-media graph client as sound (§11,
`src/common/iom.c`), or the unit's test tools: `testapp-file` and
`testapp-cmdline` from `/mnt/efs-system/bin` (`GetTrackInfo`,
`GetVideoInfo`). `testapp-file` always exits 1, buffers its stdout fully
and ignores SIGTERM. Judge it by its `FINISHED` line.

**Live streaming (works).** The container is a
constant-sample-size MP4 (CS-MP4, `media/csmp4.py`): `ftyp`, `moov`, then a
32-bit `mdat`; one constant `stsz` size; every frame padded to one size S
with a filler NAL; `moov` declaring far more frames than exist. An app's own
QNX resource manager serves it (`src/common/stream_server.cpp`;
`src/common/qnx/sys/pm.h` makes `<sys/iofunc.h>` compile), with `st_size` =
the declared total and reads that block until the frame exists. io-media
reads it sequentially in 64 KB, ~2.7 frames ahead, waits out pauses of at
least 5 s, and adds ~0.5 s of steady latency. After a pause the picture
skips the ~9 frames that were queued, so a live source must keep a steady
frame rate. A file growing on the card does not work (EIO). The
whole path is one class, `src/common/hw_stream.h` (Makefile group
`LIVE`, C++ apps only): push Annex-B frames, it builds the header from the
SPS/PPS, pads, serves, plays, shows, and fills gaps with skip frames.
[phone-mirroring.md](phone-mirroring.md) §2, §7.8–7.10,
[src/hello9/README.md](../src/hello9/README.md).

## 11. Sound

**The one audible output is the io-media mixer output
`mixer:DSPOUT_TDM1_20_SAD?delay=130`**, played from a file (WAV works, from
`/tmp` too). Two ways, both confirmed:

- the unit's `testapp-file -o mixer:DSPOUT_TDM1_20_SAD?delay=130 file.wav`
  (via `proc_start`), or
- your own graph, no library needed (`src/common/iom.c`, codes read from
  `testapp-file`): `open("/dev/io-media/graphs/trackplayer/<name>",
  O_RDWR|O_CREAT|O_EXCL)`, then devctls to attach the output URL, attach
  the input (the file extension picks the parser), play, and read events
  (`INPUT_EOF`, `TIME`, `STATUS`, `FINISHED`, `ERROR`) from the same fd.
  Closing the fd destroys the graph.

How it behaves:

| | |
|---|---|
| Next to the radio / Bluetooth music | **replaces** them while the file plays; they come back ~0.2 s after |
| Level | follows the car's volume knob |
| Graph volume devctl | returns EOK, **does nothing** (io-media's `mixer_set_volume` calls a stub). To be quieter, scale your samples. |
| Queued files | one `FINISHED` per queue; each file adds ~350 ms of silence (no gapless queueing) |
| Start latency | `STATUS playing` +24 ms after play, first `TIME` +480 ms |

Other outputs: `DSPOUT_TDM1_51_SAD` was held by the MME ("Already in use"); `TDM1_51` (no SAD)
mutes the car; `TDM1_20` (no SAD) cuts the radio; `TDM2`/`TDM3` play but are
never heard. **QSA / io-audio** (`libasound`, `/dev/snd/pcmC0D5` "tones1"
and five more devices) accepts and plays streams to the FPGA, but nothing
is heard: the amplifier only mixes sources MMI3GApplication's audio manager
switches on (inferred). `sdk/include/sys/asoundlib.h` has the reconstructed
QSA ABI if you need it. **Live PCM output (a stream rather than a file) is
not solved.**

Details: [platform-notes.md](platform-notes.md) §9, [src/hello5/README.md](../src/hello5/README.md).

## 12. Input: knobs and buttons

All user input arrives as 27-byte state messages on `/dev/ipc/ch8`. `quit.c`
reads it. Pass a callback to `quit_init_ex()` to receive every message on
its thread. `src/hello7/keys.c` decodes them.

| Byte | Control |
|---|---|
| 6 / 7 | main rotary knob right / left: detent **counts** (a fast turn sends `02`) |
| 4 / 5 | volume knob up / down: counts |
| 1, 3 | buttons as bitmasks on press, then an all-zero message on release (~200–350 ms). `b3 0x04` likely MENU, `b1 0x02` likely top-left soft key (both unconfirmed) |
| 14–15 | `01 02` normally. Byte 15 going `02 → 03 → 00` came with the car switching off (inferred power state) |
| 16–26 | state, not controls |

The **HMI still acts on every knob and button** while your app is on
screen. Keeping input from the HMI is open. Don't use MENU/BACK in an app
design yet.

## 13. USB: talking to a phone

`io-usb` is QNX's host stack; apps link `-lusbdi` (`libusbdi.so.2`). Rules
read out of the binaries ([usb-stack.md](usb-stack.md)):

1. Callbacks run on **one** library thread (insertion, removal,
   completion, in order). Only queue events there and work on your own
   thread.
2. **Expect to reopen on the same device.** The media launcher probes new
   devices, may detach yours (which aborts your URBs) or reset it. Retry a
   few times (the receiver tries 5).
3. **Retry `usbd_close_pipe`/`usbd_detach` on `EBUSY`** until libusbdi's
   I/O counters drain, or io-usb holds the port.
4. No one can lock you out, and MTP won't take an accessory interface.
5. EP0 transfers are synchronous; bulk completes asynchronously.
6. Buffers must come from `usbd_alloc()` (the library DMA-maps them).

**Android Open Accessory works** (`src/audi_stream_receiver/aoa.c`): connect
with a wildcard filter, on insertion send `GET_PROTOCOL` (51),
`SEND_STRING` (52) ×6, `START` (53). The phone re-enumerates as
`18d1:2d00/2d01` with one bulk IN/OUT pair. No root and no USB debugging
needed. Android opens the app whose `accessory_filter.xml` matches
manufacturer `mmi3g`, model `audi_stream_receiver`. Observed: the first
connect may need two `START`s, and an accessory session no app opens drops
after ~18 s. Both are handled by retrying.

**Protocol** (`proto.h` = `android/.../Proto.kt`): frames of
`type u8 | len u16 LE | payload`, at most 2048 B. `HELLO`/`HELLO_REPLY`,
`VIDEO_CAPS`, `VIDEO_START` + `VIDEO_DATA` chunks, `VIDEO_ACK`,
`VIDEO_STOP`, `VIDEO_DETAILS`. Types `0x02`/`0x03` are retired: don't reuse
them.

**Screen streaming, measured:** JPEG/PNG pictures, two in flight,
decoded on the MMI with stb_image. ~3 fps at 80–160 ms latency, 0 bad
pictures in 230. JPEG 800×368 decodes in ~61 ms, PNG in ~46 ms.
About 100 ms of MMI work per picture puts its ceiling near 10 fps; the
phone sets the rate. **Hardware H.264**: 25 fps, ~0.6 s lag, MMI
CPU ~24 % ([src/audi_stream_receiver/README.md](../src/audi_stream_receiver/README.md)). Streaming stops when the phone locks (Android revokes
MediaProjection).

**Desk testing:** `make aoa-host` makes the PC play the MMI's part, so
phone-app bugs and MMI bugs can be told apart without the car.

## 14. Using the unit's own tools and services

- Tools in `/mnt/efs-system/bin` are served decompressed by `inflator`.
  The apps prefer the unit's copies. `make sd` puts this firmware's
  inflated copies on the card as a fallback (`FWTOOLS_<app>` in the
  Makefile).
- Start them with `proc_start()`/`proc_shell()` (spawn, output to a file,
  timeout). Useful: `testapp-file`, `testapp-cmdline`, `sloginfo`,
  `ShowVideoMemory`, `memusage`, `hbhogs`, `pidin`. **Not**
  `ShowDisplayables`: `ShowDisplayables 0` blanks the screen.
- An app can be a QNX resource manager (`iofunc`/`dispatch`) and serve
  paths that unit services read, as hello9 does for io-media.

## 16. Reverse-engineering workflow

- **Ghidra** decompiles SH4. IDA has no SH4 decompiler (fine for xrefs and
  disassembly). Headless Ghidra hangs on full SH4 analysis of small
  binaries: use `-analysisTimeoutPerFile 90` and create functions at
  prologues. For MMI3GApplication, `-analysisTimeoutPerFile 1500` completes
  (about 11 minutes).
- `tools/DumpDecomp.java` resolves the SH4 PIC idiom `(literal + pc)` to
  call targets and strings. `tools/resolve_decomp.py` then replaces
  Ghidra's truncated `PTR_s_…` labels with the full strings and
  `PTR_FUN_…` slots with their targets, so log and trace strings become
  greppable.
- Existing dumps are in `third_party/decomp/P1001_rev51/` (gitignored, with
  a README).
- Firmware `.so` files lack section headers: carve a window and
  `objdump -b binary -m sh4` it (§5). An ELF with a corrupt section table
  loads in Ghidra after zeroing `e_shoff`/`e_shnum`.
- efs images: `tools/f3swalk.py` extracts by extents; compressed efs
  files inflate with `tools/qnx_inflator.c`.
- Every ABI you reconstruct gets `_Static_assert`s for size and offsets,
  and a short write-up of where each offset came from.

## 18. Contributing to MMI3G-Toolkit

What a native contribution should keep:

- **Docker only.** Any new toolchain gets its own image and its own
  Makefile next to its sources; the parent Makefile only delegates.
- **One app = `src/<app>/` + README**, shared code in `src/common/` linked
  by group, a `sd/apps.conf` line, host tests in `tests/` for every pure
  part.
- **Header guards = directory + file** (`COMMON_LOG_H`, `HELLO5_PULSE_H`).
  A bare `SCREEN_H` already collided with a constant.
- **Neutral identities:** run dir `/tmp/mmi_apps`, AOA manufacturer
  `mmi3g`, package ids under `mmi3g.*`.
- **Label claims** confirmed / inferred / unverified, and say which
  measurement or binary address backs each one. Write results up in `docs/`, so
  nothing needs re-testing.
- **Give the screen back.** Every exit path unregisters its displayables
  and restores the HMI's show list, crash or not (displayables outlive the
  process).
- **Nothing safety-relevant:** don't hold the video path or the screen in a
  way that could hide the rear camera, and don't touch flash, `srv-starter`
  or system binaries from an app. Everything here runs from the SD card and
  changes nothing on the unit.

Before upstreaming, decide:

1. **Where the project lives** in the toolkit (e.g. a top-level
   `native/`). The Makefile's `REPO`, `OQ`, `FW` and `FWEFS` paths assume
   `dev/<dir>/` today.
2. **How users get the firmware-derived inputs.** The stubs need only
   each library's dynamic symbol table, but they come from Audi firmware,
   as do the inflated unit tools. Either users extract their own firmware
   with the toolkit's tools (`tools/inflate_ifs.py --extract`), or the
   repo ships generated stubs.
3. **Packaging as a module.** Toolkit modules are `modules/<name>/` with
   `module.json` (`run_script`, `payload_dirs`, options), scripts and a
   README; `builder/build_sd.py` assembles cards. A native app fits as a
   module whose payload is `bin/` plus a run script modelled on
   `sd/run.sh`.
4. **Updating `docs/CUSTOM_APPS.md`.** Its "Mechanism 5: Native code" still
   describes the toolchain as an unsolved plan (official SDK or building
   from openqnx, linking on the target). This guide replaces that section.
