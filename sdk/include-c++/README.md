# C++ for the MMI: `shle-nto-g++`

`shle-nto-g++` (a link to `shle-nto-gcc`, picked by name) compiles C++ for
the MMI with Debian's `g++-16-sh4-linux-gnu` and links GCC 16's
**`libstdc++.a` statically**. Like C, it needs nothing from the car beyond
`libc.so.2` and `libm.so.2`. The default standard is GCC 16's, `gnu++20`.

```sh
docker run --rm -u $(id -u):$(id -g) -v $PWD:/src mmi-sdk \
    shle-nto-g++ -O2 -o app app.cpp -lgf
```

As with any g++, `.c` files are compiled as C++. To mix in C files, put
`-x c` before **each** one: g++'s driver applies it to the next file only.
The Makefile's `CXX_APPS` rule does this.

**Status:** builds, and `src/hello8` (18 checks) passes on the build host
with glibc's libstdc++ (`make test`). On the car (2026-10-25) hello8 did
not load: a `STB_GNU_UNIQUE` symbol from `libstdc++.a` (see below), fixed
since. **On 2026-10-30 all 18 checks passed on the car**
([`src/hello8/README.md`](../../src/hello8/README.md)), and `atomics
stress` confirmed the gUSA problem described below: gUSA `fetch_add` lost
9 % of its updates, SH-4A LL/SC none. The SDK builds with LL/SC since. **For app writers:**
[`docs/cpp-apps.md`](../../docs/cpp-apps.md) has the rules.

## Why not the car's own C++ libraries

The unit has `libstdc++.so.5` (GCC 3.3 ABI) and Dinkumware `libcpp.so.4` /
`libecpp-ne.so.4` (MMI3GApplication uses the Embedded C++ one, no
exceptions). GCC 16's headers fit neither, so libstdc++ comes along in the
binary: about 180 KB stripped even for an empty `main()` (exception
support and the runtime shim), about 200 KB for a program using
containers, strings, exceptions and threads.

## How it fits together

Debian's `libstdc++.a` and its headers are built for **glibc on sh4
Linux**. Code generation is the same ABI as QNX (see the main README), so
what is left is where libstdc++ meets the C library.

**Headers.** `$SYSROOT/usr/include-c++` sits around libstdc++'s own
headers. Search order: `pre/`, libstdc++, `post/`, then the QNX headers.

| File | Why |
|---|---|
| `pre/bits/os_defines.h` | replaces the gnu-linux one, which needs glibc's `<features.h>` |
| `pre/bits/c++config.h` | the real one, then `#undef`s what QNX 6.3's libc lacks (TLS, futex, `aligned_alloc`, `quick_exit`, C99 wide-char and complex functions, `timespec_get`, the pthread clock waits) |
| `pre/bits/c++locale.h` | generated by `build-sysroot.sh`: libstdc++'s own, with glibc's `__locale_t` spelled out as the same pointer type, so mangled names still match `libstdc++.a` |
| `pre/bits/ctype_base.h` | glibc's `_IS*` ctype bits (QNX's `<ctype.h>` has none) with glibc's values, before libstdc++'s own |
| `post/stdlib.h` | QNX declares `strtof`, `strtold` and `lldiv_t` in `std` only; exports them to `::` for `<cstdlib>` |
| `post/stddef.h` | C11 `max_align_t` |
| `post/pthread.h` | `PTHREAD_MUTEX_INITIALIZER` with a cast: `0x80000000` into an `int` is a narrowing error in C++ |
| `post/math.h` | a C99 `<math.h>` for the unit's `libm.so.2` (Dinkumware, every C99 function); openqnx has none |
| `post/libintl.h` | declarations only, for `<locale>`, which C++20's `<chrono>` includes |

`_QNX_SOURCE` is defined for C++: the QNX headers show their C99 and POSIX
declarations by `__STDC_VERSION__`, which C++ doesn't define.

**Runtime shim.** `cxxrt-qnx.o` (from `sdk/cxxrt.c` and
`sdk/cxxrt-std.cpp`) is linked ahead of `libstdc++.a`, so where both define
a symbol, ours wins.

| Symbol | Why |
|---|---|
| `__cxa_get_globals(_fast)` | per-thread exception state. libstdc++ keeps it in a `__thread` variable, and QNX 6.3 has no TLS, so ours uses a pthread key |
| `__cxa_guard_acquire/release/abort` | function-local statics. libstdc++'s wait on a Linux futex; ours use one recursive mutex |
| `_dl_find_object` | how the unwinder finds `.eh_frame_hdr` (glibc 2.35+). Ours answers for the executable: `PT_GNU_EH_FRAME` from our own program headers |
| `std::condition_variable` members | libstdc++.a's constructor writes a 48-byte glibc `pthread_cond_t` into an object sized for QNX's 8 bytes; ours are the same members compiled with QNX's layout |
| `std::__once_functor`, `__once_proxy`, ... | `std::call_once` without TLS (GCC's own non-TLS code) |
| `__clock_gettime64`, `__nanosleep64` | Debian's glibc has a 64-bit `time_t`. These also map Linux clock ids to QNX's (Linux `1` is `CLOCK_MONOTONIC`, QNX `1` is `CLOCK_SOFTTIME`) |
| `gettext`, `__errno_location`, `stderr`, `secure_getenv`, `strerror_r` (GNU), `__isoc23_strto*`, `getentropy`, `arc4random`, `__ioctl_time64`, `get_nprocs`, `__libc_single_threaded` | glibc names mapped to QNX's or stubbed |

Weak references to the transactional-memory runtime (`_ITM_*`) stay
unresolved. QNX's loader sets them to 0, and nothing calls them
(confirmed on the car, 2026-10-25: they were not among the unknown
symbols).

**After the link.** `libstdc++.a` defines some template statics with
binding `STB_GNU_UNIQUE` (`std::string`'s `_S_empty_rep_storage`, `npos`,
...). GNU ld exports such a symbol to `.dynsym` and marks the file OS/ABI
GNU. QNX 6.3's loader doesn't know the binding and reports the symbol as
unknown (hello8 on 2026-10-25). `sdk/qnx-elf-fix.py`, run by the wrapper
after every link, rewrites `UNIQUE` to `GLOBAL` (equivalent in an
executable) and the OS/ABI back to System V, and fails the build on IFUNC
symbols or a TLS segment.

## What works

Everything hello8 checks (`src/hello8/checks.cpp`; all passed on the car,
2026-10-28):
static constructors and destructors, function-local statics, exceptions
(including across threads, `exception_ptr`, nested), RTTI and `dynamic_cast`,
aligned `new`, `std::string`/`string_view`, `to_string`/`stoi`/`stod`, all
containers, `<algorithm>`, `<numeric>`, ranges and views, `span`,
`optional`/`variant`/`any`, `std::function`/`bind`, smart pointers,
`<cmath>`, `<complex>`, `<random>`, `<chrono>` (clocks, `sleep_for`,
calendar), `std::thread`, mutexes (plain, recursive, shared, `scoped_lock`),
`condition_variable`, `call_once`, `<atomic>`, `<charconv>`.

## What doesn't

- **iostreams, `<sstream>`, `<format>`, `std::locale`:** libstdc++.a's
  locale code is glibc's (`__newlocale`, `__uselocale`, the ctype tables
  inside glibc's locale struct). The link fails. Use `snprintf`.
- **`thread_local`:** no TLS on QNX 6.3. It compiles and links, then
  touches a thread pointer nobody set up.
- **C++20 waiting and semaphores** (`atomic::wait`, `std::semaphore`,
  `latch`, `barrier`, `jthread`'s stop tokens) and **`std::async` /
  futures:** libstdc++.a's code waits on a Linux futex. The link fails
  (`syscall`).
- **`notify_all_at_thread_exit`:** the link fails on duplicate
  `condition_variable` symbols.
- **64-bit atomics** (`std::atomic<long long>`): not lock-free on SH4.
  They need libatomic, which isn't linked: the link fails
  (`__atomic_fetch_add_8`).
- **gUSA atomics are not atomic across a preemption (confirmed on the
  car), so the SDK builds with SH-4A LL/SC.** GCC's sh4 Linux default is
  `-matomic-model=soft-gusa`: short sequences that the *Linux* kernel
  restarts if they are interrupted. QNX's kernel saves and restores the
  registers and doesn't restart them (openqnx
  `services/system/ker/sh/kernel.s`). In hello8's `atomics stress` on
  2026-10-30, 4 round-robin threads lost 11.6 M of 129 M gUSA
  `fetch_add`s, and none with `movli.l`/`movco.l` (QNX's own `atomic_add`
  uses them too). Since then `shle-nto-gcc` passes `-m4a
  -matomic-model=hard-llcs -Wa,--isa=sh4a` for everything we compile, the
  headers' inlined `std::atomic` and `shared_ptr` counts included. What
  is precompiled into `libstdc++.a` / `libgcc_eh.a` keeps gUSA: COW
  string and `exception_ptr` counts (exception messages), `std::thread`
  start-up, `set_terminate` and co., and the unwinder's frame registry
  (`make gusa-scan`). A signal delivered to a handler while one of those
  runs kills the process, because `r15` holds the gUSA marker and the
  kernel's signal-frame bounds check in `ker/nano_signal.c` fails.
  Signals taken with `sigwait()` are not affected. Rebuilding those
  archives with LL/SC would close this (`docs/TODO.md`).
- **An exception escaping a `call_once` callable** ends in
  `std::terminate`: it would have to unwind through QNX's `pthread_once`,
  which has no unwind tables. The same goes for throwing through any C
  library callback (`qsort`, ...).
- **`std::random_device` default:** no `getentropy` on QNX 6.3. Use
  `std::random_device("/dev/urandom")`.
